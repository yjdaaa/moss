# MOSS 实机验证顺序与操作手册

本文是**唯一按“接几台设备”排序的实机验证执行顺序**：从一台电脑开始，逐台加设备，最后才是“电脑 + 小智 + 激光机”三件套一起跑。
逐项勾选状态仍记在 [融合实施 TODO](moss-fusion-implementation-todo.md)：§2a 是待实机测试清单（HW-01～HW-20），§10 是最终统一真实环境验收（FINAL-01～05）。本文只规定**顺序、前提、操作和判据**，不重复记录进度。

设计依据：内置语音看 [内置语音技术书](moss-native-voice-spec.md) 与 [NV10～NV19 实施细则](moss-native-voice-implementation.md)；外部链路与审批看 [融合技术书](moss-desktop-fusion-technical-spec.md)。规则与结果状态以根目录 [`AGENTS.md`](../../AGENTS.md) 为准。

***

## 一、为什么必须按这个顺序

1. **先排除单机问题**：接线、驱动、端口、权限、版本这类问题在“只有电脑”时最容易看清。混在一起测，出一个错要看三处日志。
2. **先排除“设备自己”的问题**：小智不接电脑也能刷机、能配网、能說話；激光机不接小智也能手动走边框。先把每台设备单独确认正常，后面的组合失败才能归因到“组合”本身。
3. **风险递增**：激光机运动会撞机、出光会烧伤，必须放在最后。语音控制激光机是风险最高的一档，只有在前面每一档都通过后才做。
4. **每一步都可回退**：任一步失败就停在当前档，不往前推进，也不用把已经通过的档重测。

**允许跳过但必须写原因**：某档缺硬件（例如没有第二台设备可测 LINK、没有真实固件可刷）时，该档标 `unverified` 并写缺什么，**不能**用模拟器结果顶替。

***

## 二、硬性安全前提（每一档都适用）

执行本文任何一条会让设备**运动、出光、刷写固件、重启或断网**的步骤前，必须同时满足：

1. 对话中已就这一档、这一次操作得到用户明确同意；批准一次只对这一次有效。
2. 人在设备旁，硬件急停/断电开关伸手可及；软件急停（顶栏“急停 0x18”或页面内急停）不能当作唯一手段。
3. 激光机：材料放稳、场地通风、护目镜到位；不需要出光的步骤明确关闭出光（走边框默认不出光）。
4. 固件刷写：设备可断电重启、能串口重刷兜底；确认固件与板型匹配。
5. 生成、预览、只读查询不需要授权；任何“发送/执行/刷写/重启”都需要。
6. 不把真实地址、串口号、令牌、账号写进本文或提交物；记录用占位符（`<moss-ip>`、`<device-ip>`）。

任何一步出现异常（撞机、异响、冒烟、设备重启、状态显示“未知”），先物理急停/断电，再记录，不重试。

## 三、结果状态怎么记

| 状态           | 含义                          |
| ------------ | --------------------------- |
| `PASS`       | 本次实际执行、现象与期望一致，且记录了时间与版本    |
| `partial`    | 部分通过，或通过但依赖了未做的检查           |
| `unverified` | 代码完成但本次没测（缺硬件、缺授权、缺条件）      |
| `FAIL`       | 实际执行且不符合期望；必须带证据（日志、截图、错误码） |

规则：

* 未测一律 `unverified`，不得写成通过；软件测试通过不等于实机通过。
* 一次实测只证明这一次。改动代码后，之前的结果作废，要重测。
* 记录必须包含：日期、MOSS 版本或构建时间、CLI/固件版本、设备型号与固件版本、实际现象、错误码原文。

**1.13 不依赖桌面窗口的等价检查（可选，先证明“执行器本身能用”）**：这条不经过语音与审批卡，只验证 MOSS 的生产执行器能不能真的把 CLI 跑起来，适合在排查“Agent 一开就失败”时先做。命令（在仓库根目录，PowerShell）：

```powershell
$env:MOSS_REAL_CLI = '<codex.exe 绝对路径>'          # 或 claude.exe

```

**2026-10-16 已实测（本机）**：codex `0.162.0-alpha.17.2` 经生产执行器跑通 31.4 秒任务并取回回答；停止用例在 8.03 秒取消、无残留进程。同一轮修掉了“运行器环境白名单比计划少 4 个键 → 真实 CLI 一律 `agent_run_failed`”的缺陷（见 CHANGELOG 2026-10-16）。**本机仍有两个非 MOSS 侧阻塞**：①codex 的 `.sandbox-bin` 缺 `codex-code-mode-host.exe`（只有旧版 `codex-command-runner-0.158.0-alpha.2.1.exe`），模型能回答但无法执行工具、改文件失败；②`claude.exe 2.1.300` 返回 403 `oauth_not_allowed_for_organization`（组织禁用订阅访问）。修好其中任一个后再做 1.13 的“真的改文件”判据，然后才做 1.9–1.12 的桌面与语音链路。另注：运行器会把含 `token` / `password` / `api_key` / `sk-` / `.env` 的**整行**输出替换成 `[redacted]`（保守策略），所以 CLI 的报错原文可能看不到，排查时需直接手动跑同一 argv。

**本档结束条件**：2.1–2.13 按实际硬件 `PASS` 或明确写 `unverified`（例如没有可刷的固件）；记录设备型号与固件版本。

## 五、多台设备 / 多份产物时的先后

1. **同一功能、多台设备**：先测一台（这台就是“先导机”），通过后再推其余的。固件推送**必须逐台确认**，一次只推一台。
2. **同一台设备、多份固件**：只推比设备当前版本**新**的；回退固件不在本流程内，需要单独授权和串口兜底方案。
3. **多个产物**（EXE / 普通 NSIS / 专用 NSIS / APK）：安装与升级验收按 `FINAL-01` 逐份记录 SHA-256 与版本；不要用旧产物冒充本次结果。
4. **代码改动后**：受影响的档位重测；与改动无关的档位不重测，但要在记录里写明本次改动范围。
